How this board works

One ticket is one unit of work: the watcher turns it into an agent thread, the host proves the result with a test command, and a passing ticket is pushed as its own git branch. Nothing runs on a server you do not own; every step is a script on this machine.

Ticket lifecycle

The watcher moves a ticket through seven statuses. It only takes the transitions listed below; a move outside them is refused by the store, not by the user interface.

backlog ─► ready ─► in-progress ─► testing ─► review ─► done ▲ │ │ │ │ └─ blocked ◄────────────┴────────────┴──────────┘
StatusMeaningWho moves it
backlogWritten down, not queued yet.You (to ready)
readyQueued; the watcher may claim it at any moment.You, or adoption
in-progressA thread is working on it. Claimed atomically, so two watchers cannot take it.Watcher
testingThe thread finished; the host is running the test command.Watcher (from the thread's status)
reviewThe test passed and a fresh reviewer judges the work; the release runs only on VERDICT: ACCEPT.Watcher
doneBranch pushed and the report written.Watcher (release)
blockedSomething needs a person: a failed test, a failed thread, a rejected approval, a missed budget.Watcher or you

A ticket in blocked either waits for a quota window it scheduled, or waits for you: fix the cause and use Move → Ready. The note and the event history keep the reason.

Test command

This field is the definition of "done" that a model cannot talk its way out of. It is a shell command the watcher runs on this machine, in the project folder, after the agent thread has finished — not inside the thread. Only the exit code is judged.

The field fills itself from the project: a Configured default wins, otherwise the board reads what the repository declares (Makefile target check/test, a go.mod build/vet/test chain, a package.json test script, Cargo.toml, pytest configuration through the project's .venv, a tests/ directory) and shows the source. What you type wins. A command that needs setup — a database, Docker, a browser, a watch process — is shown as a suggestion but not filled. The watcher never invents a command or derives one from the ticket text; a project with nothing declared asks, and an empty field blocks at testing rather than pretending.

Exit codeWhat happens
0The last 40 lines are stored as proof, and the ticket moves to review.
anything elseThe ticket goes back to in-progress with the failing output in its note.
empty fieldThe ticket blocks at testing with test_cmd is empty: the watcher never guesses a command.

So the command has to be runnable from the project directory and end with a status:

make check
python3 -m unittest discover -s tests
go test ./...
npm test -- --run

Prefer the same command your CI runs, so a green ticket means a green pipeline. The proof is a marker plus a timestamp and the output tail ([PASS] 2026-11-26T…); release refuses a ticket whose proof is not [PASS].

Why outside the thread? A test the agent runs could be shaped by the agent. Running it from the host makes the evidence independent of the model's opinion.

Harness, model and presets

The pickers are not a hard-coded list. They come from T3's own provider cache (~/.t3/caches/<instanceId>.json), so they show exactly the harnesses T3 reports as installed and enabled. A disabled harness is rejected by the API even if you send it.

Resolution order, strongest first:

  1. provider + model stored on the ticket;
  2. the ticket's preset (model_profile), a named pair in ~/.config/t3-workflow/config.json;
  3. defaults.profile from the same config.

A half-filled pair (provider without a model) is rejected when the ticket is created. Presets are a shortcut, not a limit: choosing one fills both fields, choosing manual keeps what you picked.

Model options such as thinking, variant or effort are shown for information only. The t3 thread start command has no flag for them, so the thread keeps the project default; this board does not pretend otherwise.

What each ticket field does

The header shows when the watcher last checked and turns amber when that is stale; Check now runs one step immediately. A running ticket has a live control that follows its thread's turn items and messages. The report is split into Summary, Test command, What was asked, Evidence, Independent review and History, each with a sentence saying what it proves.

Reading is part of the dialog: report opens the report as a server-rendered page, thread shows the thread's title, project and status beside its id, and every path field has a Browse… picker that reads this machine (names only, token-guarded, system and hidden paths refused).

Independent review

Before anything is pushed, a second thread judges the work in a fresh context. The watcher starts it, in the same project folder, with the ticket's own harness and model by default (verification.profile names another preset if you want one). It receives the ticket, the recorded test proof, git status and git diff HEAD — not a summary written by the dev model — and must end its reply with exactly one line:

VERDICT: ACCEPT  or  VERDICT: REJECT
OutcomeTicket
ACCEPTrelease runs: branch pushed, report written, done. The card then reads review accept · first attempt; the budget only appears for a rejection (reject · attempt 1 of 2), because a spare attempt is not work left undone.
REJECT with attempts leftfindings are sent into the dev thread; ticket returns to in-progress.
REJECT at maxAttemptsblocked, with the findings in the note and the report.
no verdict line, reviewer failed, asked a question, or timed outblocked. A reply that does not decide is never an acceptance.
project changed during the reviewblocked: the verdict no longer belongs to that tree.

Defaults: maxAttempts 2, timeoutMinutes 20, maxDiffBytes 60000, in ~/.config/t3-workflow/config.json under verification. enabled: false restores the plain flow where review releases directly.

T3 0.1.9 has no read-only runtime mode, so the reviewer runs with the project's normal permissions. The guard is outside it: the watcher fingerprints the tree before and after and refuses a verdict if the tree moved. The measurements are in docs/readonly-verifier.md.

Editing and deleting

Every card that is not done has an edit control. It opens the same dialog, prefilled, and saves through POST /api/tickets/<id>/edit: title, context, test command, priority, attachment, preset and harness/model. A ticket a stage is working on needs the human override (the board sends it); a done ticket is final, because its report is the record.

Delete lives inside that dialog and asks for confirmation. The report is written before the row is removed, a deleted event stores a snapshot of the ticket, and GET /api/report/<id> keeps serving the file — the evidence outlives the ticket.

Project defaults

A project can carry a test command and a preset in ~/.config/t3-workflow/config.json (projects.<title>). The dialog prefills them when you pick the project, and tickets/cli.py add uses them when the flags are omitted, so a ticket can be just a title and a target. Defaults remove the typing, not the proof: a ticket with no test command still blocks.

Priority

ValueUse for
1 — UrgentSomething is broken, or it blocks somebody else.
2 — HighPromised for today.
3 — NormalThe default queue.
4 — LowPolish and cleanup.
5 — SomedayIdeas that should not compete for the slot.

The watcher always takes the lowest number first, then the oldest ticket at that level.

Approvals

Ticking Needs my approval makes the dev stage ask instead of starting. The request appears on the board card (Approve / Reject), in Telegram (/approve <id>, /reject <id>), and in the ticket's event history.

Approvals are one-shot: the first answer wins and a second one is refused. A rejection moves the ticket to blocked; an approval lets the watcher proceed on its next step.

Approval requests that appear inside a running T3 turn are a different mechanism and are still answered in the T3 interface: the CLI has no command to answer them.

Creating, adopting and registering

A ticket without a thread starts a new one. A ticket that already carries a thread continues that same thread: the watcher sends the ticket text into it and records a continued event. One ticket never owns two threads.

Use Adopt thread when an agent already produced work, or when you want to continue an earlier conversation; create a ticket when the work is new or independent.

Registering a project

Agents may only work in folders T3 knows about. Register project takes a name and an absolute path that already exists, then runs t3 project add: T3 stays the owner of the project, and this board only mirrors the result. A folder that already belongs to a project is refused in the dialog, naming that project, instead of failing with a raw CLI error. Point it at the repository root, because the agent works there and the test command runs there. A registered project appears in the ticket dialog immediately.

A folder that is not a git repository can be registered, but the release stage will fail loudly when it looks for a remote; that is intentional, so nothing is ever pushed nowhere.

Limits, failures and overrides

  • watcher.maxConcurrent (default 1) keeps at most that many tickets in-progress; extra tickets wait in ready.
  • limits.maxInProgressMinutes moves a ticket that overran its time budget to blocked, so a stuck run cannot hang the queue.
  • A failing thread, a failed test or a broken T3 call moves the ticket to blocked with the reason in the note; nothing is retried silently.
  • Release pushes ticket/T-xxxx-… to origin and never the base branch; a repository without a remote fails loudly and the ticket stays in review.
  • Force move is the human override. It skips the state machine and is recorded as a forced event, so a report can tell a decision from a normal transition.

When something fails

Failures a retry can fix do not stop the queue; they go back into the loop with a counter on the ticket.

Telegram announces the work as it moves — acknowledged when claimed, a retry notice, the verdict, and on done the markdown report as a document. Ticket-driven messages start with 🤖 ticket automation; replies to commands you typed do not, so the two are easy to tell apart.

Deleting here or in T3

The board and T3 own different things, so deletions do not cascade into each other.

You deleteTickets and reportsT3
A thread in T3kept; the watcher blocks the ticket with thread … no longer exists in T3gone
A project in T3kept; the card shows project missinggone
A ticket (board or CLI)row removed after a snapshot; report keptuntouched: a thread is work history

A usage limit retries itself: the ticket blocks with a retry time and the watcher puts it back in ready after the backoff window, a bounded number of times. Any other blocked ticket comes back with Move → Ready on its card.

Register project → Existing projects can remove a project: it asks you to type the project title, then runs t3 project remove --force, which deletes the project and all of its threads. Tickets and reports are kept and marked project missing.

Deletion is not mirrored 1:1, and cannot be: T3's CLI has no per-thread delete (t3 thread --help lists only list|start|send|show), so a board action cannot remove a thread. Only t3 project remove --force deletes a project's threads, and that is project-wide. The board therefore keeps the ticket and its report, and shows what T3 did: a deleted thread blocks the ticket, a missing project gets a badge.

What is not built yet

  • Per-ticket model options (thinking, variant, effort): no CLI flag exists.
  • Images as attachments. t3 thread send accepts text; a path is passed instead.
  • Pull-request creation and deploy. Release stops at a pushed branch, a compare link and a PR body file.
  • A PDF report. The report exists as markdown and is delivered as a Telegram document; a PDF renderer would add a dependency this machine does not need.
